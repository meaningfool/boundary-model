# Open list

Each round takes every provider or component on the list, lists its parts, tests each part against the component guideline of use-boundary-model (keeps state only it changes, or makes decisions only it makes, and the other parts reach it only through what it exposes), and opens it when two or more parts pass.

## Round 1 (Level 2): Cloudflare OS

Evidence read: packages/workshop-shared/src/api.ts (the Workshop API), packages/workshop-shared/src/gatekeeper.ts (the gatekeeper contract), packages/workshop-backend/src/auth/auth-vendors.ts (the registry: buildGatekeeperVendorMap scans GATEKEEPER_* bindings), packages/router/src/index.ts, every in-corpus package.json (internal dependencies), each Worker's cloudflare.config.ts (Durable Object classes and bindings), vite.config.ts lint overrides (the only enforced seam: agent-facing *types.d.ts and *-binding.d.ts must be self-contained), history since 2026-05-29 (867 commits; history-files.txt).

Parts and verdicts:

- Kernel (packages/workshop-backend, with its contracts in packages/workshop-shared): COMPONENT. Keeps users, workspaces, chats, gadgets and their code history, blueprints, sharing grants, admin settings and the audit log, and only it changes them (Durable Object classes in packages/workshop-backend/cloudflare.config.ts migrations; KV BLUEPRINTS and AVATARS, R2 BLUEPRINT_CONTENT). The web app reaches it only through PublicApi/AuthenticatedApi in api.ts over Cap'n Web (packages/workshop-backend/src/server.ts fetch() and PublicApiImpl); gatekeepers reach it only through ApprovalQueue, ObservationAuthorizer and GatekeeperConnectCallback in gatekeeper.ts. REVIEW.md "High-scrutiny areas" names it the kernel with its own bar.
- Gatekeepers (packages/gatekeeper-github, gatekeeper-mcp, gatekeeper-mcp-portal, gatekeeper-context, gatekeeper-scheduler, and the sixteen excluded drivers): COMPONENT WITH VARIANTS. Each keeps its connected accounts' credentials and its own per-resource state (UserAccount/GitHubGatekeeperImpl/GitHubHookDriver in gatekeeper-github/cloudflare.config.ts; McpAccount/McpGatekeeperImpl in gatekeeper-mcp and gatekeeper-mcp-portal; ContextCollectionDurableObject, UserLibraryDurableObject, LibraryRegistryDurableObject, ContextGatekeeper in gatekeeper-context; ScheduleDriver, SchedulerGatekeeper in gatekeeper-scheduler) and decides which actions are observations and which wait for approval (gatekeeper-github/README.md "Auto-approval"). The kernel reaches every one only through GatekeeperVendor, GatekeeperUser and Gatekeeper<Session> in gatekeeper.ts, registered alike by buildGatekeeperVendorMap; no kernel code names a vendor except the billing flow's CLOUDFLARE_VENDOR_ID (user.ts). They fulfil one contract, so they are one component with variants. History agrees: gatekeeper-github changed with the excluded drivers in 60 of its 67 commits, gatekeeper-context with gatekeeper-scheduler in 41 of 55.
- Workshop web app (packages/workshop-frontend): NOT A COMPONENT. A client that presents the Kernel's capabilities and hosts gadgets' and gatekeeper apps' sandboxed iframes, relaying their RPC (api.ts header comment, GadgetHost); it keeps no domain state of its own (only the session token in local storage). Part of the interface "Workshop web app".
- Router (packages/router): NOT A COMPONENT. Passes requests on by path prefix (src/index.ts); routing machinery.
- Gatekeeper kit, MCP shared library, configurator UI runtime (packages/gatekeeper-kit, packages/mcp-shared, packages/configurator-ui): NOT COMPONENTS. Libraries the gatekeeper variants build on (gatekeeper-kit/package.json "Building blocks for gatekeepers ... Not a deployable Worker"; mcp-shared/README.md; configurator-ui/AGENTS.md). The kernel imports only gatekeeper-kit/git-pull-transfer (worktree-git.ts), a helper.
- PDF renderer (packages/pdf-renderer): NOT A COMPONENT. A stateless Worker with "no route, no storage and no bindings of its own" (README.md) that draws PDF pages for one excluded driver (scripts/release/manifest-lib.ts INTERNAL_WORKERS). A library in its own isolate.
- Bundled blueprints (packages/bundled-blueprints): NOT A COMPONENT. Gadget source code the Kernel installs as blueprints on first request (workshop-backend/AGENTS.md "Bundled blueprints"); content, the built-in instances of the Blueprint resource.
- Gadgets (user-written apps run by the Kernel in Dynamic Worker facets): NOT A COMPONENT OF THE PROVIDER. Their code and storage are the user's, created at run time; to the consumer they are the Gadget resource. The part that runs them is inside the Kernel (overseer.ts, LOADER binding).
- Shared libraries (packages/observability, packages/error-reporting, packages/typed-storage, packages/office-content, packages/ui): NOT COMPONENTS. Libraries (their package.json descriptions; observability/AGENTS.md).
- Engineering tooling (packages/api-schema, packages/integration-tests, packages/workshop-evals, scripts, .github, .agents, root build config): out of the perimeter; api-cli is the thin client that is an interface (see notes-level1.md).

Decision: two parts are components (Kernel, Gatekeepers), so Cloudflare OS opens. Kernel and Gatekeepers go on the list for round 2.

### Kernel: parts and verdicts

- User account (UserDurableObject, user.ts; storage-schema/user-storage.ts): COMPONENT. Keeps one user's identity and sessions, password hash, connected accounts (the GatekeeperUser stubs), AI model settings, workspace list and shared-workspace records, blueprint library, outputs index, notification devices, unread state and daily usage count; only it changes them. Others reach it through its stub methods (listed in open-list from user.ts: createAccount, login, authenticate, connectAccount, getGatekeeperClassFor, createResourceGatekeeper, getChatContext, recordSharedWorkspaceOpen, messageArrived, publishNotification, syncWorkspaceOutputs, openForAdmin, ...). Decides who is signed in and which resources are enabled before a capability is minted (#assertResourceEnabled, REVIEW.md).
- Workspace (OverseerDurableObject and OverseerImpl, overseer.ts; storage-schema/overseer-storage.ts, overseer-migrations.ts): COMPONENT. Keeps one workspace's chats, gadgets and their code history, gatekeeper connections, the action queue, hooks, sharing graph and observers; only it changes them. The web app reaches it only through Overseer (api.ts) returned by open(); gatekeepers through ApprovalQueue and ObservationAuthorizer (ApprovalQueueImpl); other kernel parts through its stub methods (open, openForAdmin, applyAdminWrite, initializeFromBlueprint, startGatekeeperSession, startHook, authorizeFetch, getOutputsForOwnerBackfill). Decides access (permission graph, docs/sharing.md) and runs the agent.
- Admin settings (AdminSettings and AdminApiImpl, admin-settings.ts, admin-config.ts, admin-access.ts, admin-writes.ts, storage-schema/admin-settings-storage.ts, bundled-blueprints.ts, deployment-updates.ts): COMPONENT. The only writer of the authoritative AdminConfig (REVIEW.md "AdminSettings is the only writer"); keeps featured blueprints and the last update check; installs bundled blueprints. Others read the KV mirror through readAdminConfig(env) or call its stub methods; admins reach it through the AdminApi capability.
- Admin audit log (AdminAuditDurableObject, admin-audit.ts): COMPONENT. Keeps the deployment-wide audit records; only it appends and prunes them; reached through append, list and stats.
- User directory (UserDirectoryDurableObject, user-directory.ts): COMPONENT. Keeps the deployment-wide list of users and workspaces behind user search and the admin listings; only it changes its tables; fed through syncUser, syncWorkspace and removeWorkspace, read through searchUsers, listUsers, listWorkspaces, workspaceListing (docs/admin-access.md "Feeds").
- API front (PublicApiImpl, AuthenticatedApiImpl, LoginAttemptImpl, server.ts fetch()): NOT A COMPONENT. Passes requests on: 58 of AuthenticatedApiImpl's calls forward to the user account's stub, openWorkspace forwards to the workspace's open(); it authenticates the WebSocket and holds no state.
- Sign-in attempt (PendingLogin and LoginConnectCallbackImpl, auth/login-flow.ts): NOT A COMPONENT. Relays a session token from a gatekeeper sign-in flow to the waiting browser; its only state is that token in transit, a step of signing in (login-flow.ts header steps 1 to 4).
- Device session handoff (auth/device-session-handoff.ts, device-session-callback.ts): NOT A COMPONENT. A step of signing a native app in; the staged credential lives in the user account (stageDeviceSessionHandoff, consumeDeviceSessionHandoff).
- AI model access (ai-models.ts, ai-gateway.ts, ai-invoke.ts, agent-compaction.ts, anthropic-compaction.ts, ai-gateway-billing/): NOT A COMPONENT. Adapters to AI model providers and AI Gateway, and the built-in LanguageModelGatekeeper and DecisionModelGatekeeper, which keep nothing (their config is in props) and pass a gadget's model calls on. Which models are enabled is decided from Admin settings' config (GatewayModels); whether a request may proceed reads the user account's daily count (usage-checker.ts imports UserDurableObject).
- Web fetch gate (FetchLoopback, fetch-loopback.ts, web-fetch.ts): NOT A COMPONENT. Every untrusted fetch passes through it, and it asks the workspace (authorizeFetch) to decide each request (docs/unified-fetch.md "Asking the workspace"). Passes requests on under the workspace's decision.
- Loopbacks (GatekeeperLoopback, GatekeeperHookLoopback, AgentSelfLoopback, GadgetTailLoopback, CodeModeTailLoopback, AgentSpawnerGatekeeper in overseer.ts): NOT COMPONENTS. Entrypoints that pass calls from sandboxed code back into the workspace.
- Blueprint catalog store (KV BLUEPRINTS and R2 BLUEPRINT_CONTENT; blueprint-archive.ts, blueprint-release.ts, storage-schema/blueprints-kv.ts): NOT A COMPONENT. Storage. Its writers are the workspace (publishes its gadgets' blueprints, overseer.ts), admin settings (installs bundled ones and keeps the featured list, bundled-blueprints.ts, admin-settings.ts), the API front (imports an archive, server.ts importBlueprint) and the user account (deletes an orphaned blueprint whose workspace is gone, user.ts). Settled as a question: no merge, since each writes records it alone creates except the orphan clean-up, which runs only after the owning workspace is gone.
- Git storage (git-cache.ts, git-codec.ts, git-chunked-blob.ts, three-way-merge.ts, diff3.d.ts, line-window.ts, grep.ts): NOT A COMPONENT. How the workspace keeps code; a storage library.
- Notifications client (notification-service.ts), gadget PDF and HTML export (browser-export.ts, gadget-export.ts, export-limits.ts, browser/), deployment update check client (deployment-updates.ts): NOT COMPONENTS. Adapters to outside services.
- Diagnostics (analytics.ts, client-errors.ts, observability.ts, agent-tracing.ts, do-retry.ts): NOT COMPONENTS. Diagnostics and plumbing, excluded as engineering tooling.

Decision: five parts are components (User account, Workspace, Admin settings, Admin audit log, User directory), so the Kernel opens.

### Gatekeepers: parts and verdicts (tested by the roles of the shared contract, across the variants)

- Connected account (GatekeeperUser with its account Durable Object: UserAccount and GatekeeperUserImpl in gatekeeper-github/src/github.ts; McpAccount and GatekeeperUserImpl in gatekeeper-mcp and gatekeeper-mcp-portal; ContextAccount in gatekeeper-context/src/library-gatekeeper.ts with the collection Durable Objects it manages; ScheduleAccount in gatekeeper-scheduler/src/scheduler.ts): COMPONENT WITH VARIANTS. Keeps one connected account's credentials and grants (storage-schema.md "UserAccount Durable Object": credentials owned by the kit's CredentialCoordinator); only it changes them; the kernel reaches it only through GatekeeperUser (connect, reconnect, commitReconnect, revoke, getGatekeeperClassFor, startResourceConfigurator, ensureResources, getAuthenticatedEmail, getVerifier) and resource facets through the variant's account methods. For the Context Library variant, it also keeps the collections the management app edits (ContextApiImpl, context-collection.ts).
- Resource gatekeeper (Gatekeeper<Session>, a Durable Object class the account mints and the workspace installs as a facet: GitHubGatekeeperImpl, McpGatekeeperImpl, ContextGatekeeper, SchedulerGatekeeper): COMPONENT WITH VARIANTS. Keeps one connection's caches, action journal and simulated results (storage-schema.md "GitHubGatekeeperImpl Durable Object", "Simulation model"); decides which calls are observations and which are actions, and simulates pending ones (write-gatekeeper SKILL.md responsibilities 4 to 6); holds only the account's id (GitHubGatekeeperImplProps.userObjectId) and asks the account for tokens. Reached only through Gatekeeper<Session> and the agent-facing session types in src/types.d.ts.
- Event source (the hook driver Durable Object with its HookController: GitHubHookDriver and GitHubHookController in gatekeeper-github/src/github-hooks.ts; ScheduleDriver and ScheduleHookController in gatekeeper-scheduler): COMPONENT WITH VARIANTS. Keeps each enabled hook's registration and delivery state (storage-schema.md "GitHubHookDriver Durable Object"; scheduler README "Persistent callbacks and retries"); decides when a hook fires (schedules) or which events it delivers; reached by the workspace only through HookController (enable, disable) and by the outside service through its webhook route.
- Vendor entry (GatekeeperVendor entrypoints): NOT A COMPONENT. Stateless; describes the vendor and starts the account's connect flow.
- Verifier (GitHubVerifier, McpVerifier, McpPortalVerifier, ContextVerifier, ScheduleVerifier): NOT A COMPONENT. A token for a user that the account mints (GatekeeperUser.getVerifier) for observer checks; part of the connected account.
- Sessions (GitHubRepoSessionImpl, McpSessionImpl, LibraryReadSession, ScheduleSessionImpl): NOT COMPONENTS. The RPC objects a resource gatekeeper hands out; part of its interface.
- Configurator UIs and management apps (src/configurator/*, gatekeeper-context/app, gatekeeper-scheduler/app, ScheduleManagementApi): NOT COMPONENTS. Clients in sandboxed frames presenting an account's or resource's capabilities.
- Connect pages and OAuth callback (gatekeeper-kit/src/connect-pages.ts, connect-handshake.ts, oauth-client.ts used by each variant): NOT COMPONENTS. Steps of connecting an account.
- Kit, MCP library and configurator runtime (gatekeeper-kit, mcp-shared, configurator-ui): NOT COMPONENTS. Libraries ("The gatekeeper owns provider facts, policy, and the assembly", gatekeeper-kit/README.md).
- Context collections (the Context Library variant's ContextCollectionDurableObject, UserLibraryDurableObject and LibraryRegistryDurableObject with the KV CONTEXT_COLLECTIONS snapshot; gatekeeper-context/src/context-collection.ts, user-library.ts, registry-do.ts, collection-access.ts, collection-kv.ts, artifact-sync.ts): COMPONENT. Keeps the collections, their documents and skills, their grants and git mirror tokens; only these classes change them (gatekeeper-context/AGENTS.md "State"); collection-access.ts is "the one collection access policy". It is reached by two roles of the variant through its methods: the account's management API (context-api.ts ContextApiImpl) and the resource's agent read session (library-read.ts LibraryReadSession), so it belongs to neither role alone. Found on a second search in this round, after the role split: it is tested in round 3.

Decision: four parts are components (Connected account, Resource gatekeeper, Event source, Context collections), so Gatekeepers opens.

## Round 3 (Level 4): components to test

- User account, Workspace, Admin settings, Admin audit log, User directory (inside Kernel)

Evidence read in round 3: overseer.ts class list and imports of workspace modules; sharing.ts SharingStorage and SharingManager constructor, and every write to storage.collaborators and storage.shareKeys (only sharing.ts and one schema migration, storage-schema/overseer-migrations.ts); overseer.ts's calls into SharingManager (getEffectiveAccess, listCollaborators, getCreatorProfile, redeemShareKey, listShareLinkRecords, computeEffectiveAccess, computeAffectedByOwnerInvitesOnly); observer-ledger.ts header and ObserverLedgerHost; auto-approval.ts header; agent.ts imports (only assertNoNul from git-cache.ts and its own display streaming from code-preview.ts) and overseer.ts's import of runAgent and AgentHooks; worktree-replica.ts and git-cache.ts class docs; user.ts and admin-settings.ts class lists; the gatekeeper-context collection, library and registry headers and their callers.

### Workspace: parts and verdicts

- Workspace host (OverseerDurableObject, OverseerImpl, OverseerClientInterface, UseOverseerInterface, GadgetClientImpl, ApprovalQueueImpl in overseer.ts; storage-schema/overseer-storage.ts, overseer-migrations.ts, overseer-git-migration.ts): COMPONENT. Keeps the workspace's chats and messages, gadgets and worktrees, connections, the action log and its auto-approval rules, hooks and observers; only it changes them; reached through Overseer (api.ts), ApprovalQueue and the stub methods. Decides each fetch (authorizeFetch) and what the use-only view allows.
- Agent (runAgent and its helpers in agent.ts, agent-catalog.ts, agent-compaction.ts, anthropic-compaction.ts, code-preview.ts, streaming-json-parser.ts, system-prompt-blocks.ts, slash-commands.ts): COMPONENT. Decides how a chat turn runs: what it sends to the model, which tool calls run and in what order, when to retry and when to compact the history. It keeps no state of its own and reaches the workspace only through AgentHooks, the interface "extracted ... to avoid cyclic dependencies" (agent.ts); the workspace reaches it only through runAgent.
- Sharing (SharingManager, sharing.ts): COMPONENT. Keeps the workspace's collaborators and share links (SharingStorage: collaborators, shareKeys), which nothing else writes outside a schema migration; decides each collaborator's effective access from the permission graph (docs/sharing.md "Permission graph"); the workspace host reaches it only through its methods.
- Observer ledger (ObserverLedger, observer-ledger.ts): NOT A COMPONENT. Its requirements "live only in the action log" (header), which the workspace host writes; its host is the whole OverseerStorage. Same store, same records.
- Auto-approval (auto-approval.ts): NOT A COMPONENT. "The single authority on whether an action may be applied without a human", but it marks the same action records the workspace host changes (AutoApprovalStorage is a slice of overseer storage). Parts that change each other's records are one component.
- Git store (WorkspaceGitCache, GitCacheImpl in git-cache.ts; git-codec.ts, git-chunked-blob.ts): NOT A COMPONENT. "The workspace's git store": storage.
- Worktree bindings and replicas (git-binding.ts, worktree-session.ts, worktree-replica.ts, worktree-git.ts): NOT COMPONENTS. RPC objects handed to sandboxed code (the GIT binding, Worktree stubs) and per-execution in-memory replica state (WorktreeReplicas); part of the workspace host's bindings.
- Gadget runtime and code execution (ui-bundle.ts, exports-session.ts, gadget-export.ts, chat-embeds.ts, chat-attachment-*.ts, read-file-result.ts, session-watchers.ts): NOT COMPONENTS. How the workspace host runs gadgets and code in Dynamic Worker facets and hands them bindings.
- Chat cache warming (chat-cache-warming.ts): NOT A COMPONENT. Provider behavior: it resends a turn's last model request before the provider's cache expires (api.ts viewChat doc).
- Admin workspace view (AdminWorkspaceViewImpl, overseer.ts; admin-view.ts): NOT A COMPONENT. A read view of the workspace's metadata for admins, run through adminViewCall(); keeps nothing.

Decision: three parts are components (Workspace host, Agent, Sharing), so the Workspace opens (Level 4).

### User account: parts and verdicts (stays closed)

Parts tested: sign-in and sessions (createAccount, login, authenticate, authenticateFromCfAccess, stageDeviceSessionHandoff); connected accounts registry (connectAccount, putConnectedAccount, disconnectAccount, getGatekeeperClassFor, createResourceGatekeeper); AI model settings (addModel, setPreferredModel, getChatContext); workspace list and shared-workspace records (newWorkspace, listWorkspaces, recordSharedWorkspaceOpen, updateTitle); blueprint library (addBlueprintToLibrary, importBlueprint, deleteOwnedBlueprint); unread state and notifications (applyReadHorizon, messageArrived, publishNotification, registerNotificationDevice); usage and billing (checkDailyLlmCount, consumeDailyLlmCall, getCloudflareBilling); outputs index (syncWorkspaceOutputs, listOutputs); admin user view (admin-user-view.ts); GatekeeperConnectCallbackImpl and GatekeeperUserSelectionExchangeImpl (user.ts). None passes: every piece of state lives in the one store of one class (storage-schema/user-storage.ts) and is changed by methods of that same class, so no part keeps state that only it changes; the two entrypoints pass callbacks and ticket redemptions on to the class; the admin user view keeps nothing and returns the account's records field by field through AdminUserViewHost (REVIEW.md).

### Admin settings: parts and verdicts (stays closed)

Parts tested: the settings store (AdminConfig, #mutateAdminConfig), the model catalog (GatewayModels in ai-gateway.ts, testGatewayProvider), featured blueprints and output formats, the bundled-blueprint installer (bundled-blueprints.ts), the update check (deployment-updates.ts), AdminApiImpl, admin writes (admin-writes.ts). None passes: the settings, featured list, formats and update status are kept in the one AdminSettings store and changed only by its methods; AdminApiImpl passes calls on to AdminSettings, the directory, the audit log and the views; GatewayModels merges the stored settings with the suggested catalog without keeping anything; the installer and update check are steps run by AdminSettings; admin-writes.ts computes a write's arguments.

### Admin audit log: parts and verdicts (stays closed)

Parts tested: recording (append, with retention pruning), listing (list), statistics (stats), text bounds (cutAdminAuditText in admin-access.ts). None passes: all work on the one audit store of AdminAuditDurableObject, changed only by append.

### User directory: parts and verdicts (stays closed)

Parts tested: the users table behind user search (searchUsers), the user_activity and workspaces tables behind the admin listings (listUsers, listWorkspaces, workspaceListing), the revision-based feeds (syncUser, syncWorkspace, removeWorkspace). None passes: docs/admin-access.md "One directory" explains that the admin listings were put beside search's table on purpose, in one store, "rather than in a second store"; one class changes all three tables.

### Connected account: parts and verdicts (stays closed)

Parts tested (across variants): the account Durable Object's credential record (the kit's CredentialCoordinator), the connect and reconnect handshake (kit connect-handshake.ts, credential-stage.ts, connect-pages.ts), the access-answer cache (KvTtlCache), the GatekeeperUser entrypoint (GatekeeperUserImpl), the verifier, the resource configurator UIs, the management APIs (Context Library's ContextApiImpl, Scheduler's ScheduleManagementApi). None passes: within each variant, the credentials and caches are in the one account object's store; the entrypoint, verifier and management APIs pass calls on to the account object or to Context collections; the handshake and cache are kit libraries; the configurators are clients.

### Resource gatekeeper: parts and verdicts (stays closed)

Parts tested (across variants): the facet Durable Object's store (caches, action journal, simulation overlay; storage-schema.md "GitHubGatekeeperImpl Durable Object", "Simulation model"), session objects (GitHubRepoSessionImpl, GitHubIssueImpl, McpSessionImpl, LibraryReadSession, ScheduleSessionImpl), the outside-service clients (GitHubApi in github-api.ts, McpClient in mcp-shared/src/client.ts), kit modules (ActionJournal, simulation, cursors, ObserverTracker). None passes: one facet store per connection, changed only by the facet class; sessions are the interface it hands out; clients are adapters; kit modules are libraries.

### Event source: parts and verdicts (stays closed)

Parts tested: the hook controller entrypoint (GitHubHookController, ScheduleHookController: state only in props, passes enable and disable on), the driver's store (GitHubHookDriver, ScheduleDriver; kit HookRegistry, HookDeliveryQueue), webhook event parsing (github-webhook-events.ts), schedule computation (scheduler-core.ts, schedule-types.ts). None passes: one driver store per variant changed only by the driver class; parsing and schedule computation keep nothing.

### Context collections: parts and verdicts

- Collection (ContextCollectionDurableObject, context-collection.ts, with collection-access.ts and artifact-sync.ts): COMPONENT. Keeps one collection's metadata, documents, skills, grants and git mirror tokens; only it changes them; answers access from its own grants, interpreted by "the one collection access policy" (collection-access.ts); reached through its methods (putContextDocument, share, setMemberRole, getAccess, search, listAgentSkills, createGitToken, syncArtifactSource, ...).
- Collection library (UserLibraryDurableObject, user-library.ts): COMPONENT. Keeps one account's index of the collections it created or was given; only it changes the index; reached through its methods (createOwnedCollection, addSharedCollection, forgetCollection, listLibrary, beginDisconnect, finishDisconnect), by the collection (grant changes) and by the account's management API. Decides the disconnect fence ("Disconnecting marks the account's library first, so a share racing it is refused", gatekeeper-context/AGENTS.md).
- Public collection registry (LibraryRegistryDurableObject, registry-do.ts, with collection-kv.ts): COMPONENT. Keeps a sharing domain's set of public collections and is the one writer of the KV snapshot sessions read ("It serializes writes to the KV snapshot"); reached through addPublic, removePublic, isPublic, syncPublic.

Decision: three parts are components, so Context collections opens (Level 4). This matches the User directory's treatment in the kernel: an index fed through its own methods by more than one part is a component.

## After round 3

Level 4 is the deepest level the caller asked for. The components found in round 3 (Workspace host, Agent, Sharing, Collection, Collection library, Public collection registry) are leaves of this map; they were not tested for a Level 5.
