Implementation details

Boundaries, level by level

A boundary is where a consumer meets a provider: what the provider offers, and through which interfaces. The first one sits between your users and your system. Open the system and the same pattern repeats inside it, between its components, one level down each time.

Each level has the same shape: a consumer, a boundary, a provider. Level 1 boundaries, with the people and systems that use yours, are external. Every boundary below is internal.

The boundary model covers the rest: what each boundary lists, how a provider opens into the next level, and the map that records it all.

02

The boundary model

The boundary model describes a system as the people and systems using it see it. This page explains its terms and the map that records them. The use-boundary-model skill holds the full definitions.

What a boundary lists

A boundary is the line across which a provider offers resources and capabilities to a consumer. There is one boundary for each consumer and provider, however many interfaces it has. Each boundary lists:

  • Interfaces: the channels the consumer uses, such as a web shop, a mobile app or an API.
  • Capabilities: what the consumer can do, to get a result. Each one works on resources, and says how: it observes, mutates, produces or reacts.
  • Areas: groups of capabilities that serve one purpose. The core area holds what the consumer comes for. Supporting areas hold what they would skip if they could, such as sign-in or settings.
  • Resources: things with a state the consumer cares about, such as an order. A provider lists each resource once, under one name.

    ConsumerThe person or system that uses the provider to get something done.
  2. 2

In text, the same boundary reads:

Resources of Store: Product · Order · Loyalty balance

Shopper <-> Store
  Interfaces: web shop · mobile app
  Shop (core)
    Browse products: observes Product
    Place order: produces Order · mutates Loyalty balance
    List past orders: observes Order
  See loyalty balance (supporting)
    See loyalty balance: observes Loyalty balance [mobile app]

Consumers and providers

  • A consumer is a role, not a person. One person can hold several roles, and roles that share goals and capabilities are one consumer.
  • The provider is what the consumer believes it is using. The apps, servers and outside services that deliver it stay inside it until you open it.
  • A boundary points one way: from the consumer, who wants something, to the provider, who delivers it. A callback that delivers a result belongs to the boundary whose capability it completes.

Levels

Level 1 shows the people and systems that use your system, and the system itself. Those boundaries are external. Every boundary below them is internal.

A provider is also a consumer one level down. To deliver what it promises, it relies on its own components and on outside services. Opening it shows that next level: its components, what each one keeps, and the boundaries between them.

A part of a provider is a component when it keeps state that only it changes, or makes decisions that only it makes, and the other parts reach it only through what it exposes. Storage, libraries and adapters to outside services are how a component keeps or reaches things, not components of their own.

What stays out

  • How the system is built. A runtime, a framework, a database or a deployment unit does not make a boundary by itself.
  • Steps of a capability. Checking a coupon is part of paying. It gives the consumer nothing of its own.
  • What the provider does on its own. A nightly job that builds a report is not something the consumer does. Reading the report is.
  • Tools that work on the system rather than with it. Build, deploy and migration tools, health checks and clean-up jobs are not boundaries. The map lists them as exclusions.

The boundary map

  • One JSON file records a system's current boundaries, at every level. A system has one map.
  • The map describes one revision of the code. A planned change does not go in it.
  • It lives at docs/boundary-map.json by default. A project that keeps it elsewhere records the path in its agent instructions, such as AGENTS.md.
  • A map is finished once a person has reviewed it.
  • The map format has a JSON schema and a checker, which needs Node 18 or later.

How the skills work together

Most of the nine skills do one of two jobs: keep a map of your system current, or plan a change on it. This page says what each skill does, and what you decide at each step.

Two jobs

Keep the map Your code extract-boundaries Draft map review-boundaries, with you Boundary map update-boundaries, after changes land, then a review
Plan a change Boundary map shape-boundaries Boundary changes slice, then refine Slices and decisions to-issues GitHub issues

use-boundary-model holds the model and the map format that the other skills load. visualize-boundaries draws the map whenever one of them needs it.

Ask in plain words, such as “map this repository's boundaries”, or name the skill. The skills keep the map at docs/boundary-map.json by default.

Keep the map

extract-boundaries: map a system

The agent
  • Reads the documentation and the code, one level at a time.
  • Checks every boundary against the code and cites the files behind it.
  • Drafts the map in a working folder outside your repository, then offers a review.
You decide
  • Which system to map.
  • What the agent may read.
  • Where the map goes.
  • Whether to start over when a map already exists.

review-boundaries: review the map

The agent
  • Sends one image per screen, from the top level down.
  • Checks each screen against the code before asking anything.
  • Asks at most five short questions per level, each with its suggestion.
  • Draws both versions when an answer would add, remove or move a part.
You decide
  • What the parts are called.
  • Which parts matter.
  • Whether the map reads clearly.

The reviewed map is written at its location only when the review ends.

update-boundaries: bring the map up to date

The agent
  • Lists the files changed since the map's revision, sorted by the part of the map they touch.
  • Reads why they changed, from commit messages and pull requests.
  • Works out what changed for each boundary, and keeps earlier decisions.
You decide
  • The changes, in a review of only what changed.

visualize-boundaries: draw the map

The agent
  • Checks the map and draws it as one page, one open box at a time, or as still images.
  • Can mark what changed since an earlier map.
You decide
  • Nothing. It draws what the map says.

Plan a change

shape-boundaries: shape a change

The agent
  • Starts from the map and reads the code behind the boundaries the change touches.
  • Asks one question at a time, the one that could change the shape most, with its recommended answer.
  • Marks each change NEW, MODIFIED or REMOVED against what exists today.
You decide
  • The answers.
  • Whether the shape is complete.
  • Which document records the decisions.

slice: divide the work

The agent
  • Proposes two or three ways to divide the work, at least one of them vertical.
  • Names the slicing smells in each, and recommends one.
You decide
  • The strategy.

refine: settle the details

The agent
  • Settles what the code and earlier decisions already answer.
  • Asks each question that has a real tradeoff, one at a time, with its recommendation.
You decide
  • Each tradeoff, until no open question would change an expected behavior or a design decision.

to-issues: write the issues

The agent
  • Looks for duplicate issues.
  • Drafts every issue with its expected behavior and proof of done, then reviews the set.
You decide
  • How the issues are grouped: under an existing parent, under a new parent, or standalone.
  • Whether to publish them.
04

Install

Install all nine skills side by side. The map scripts find use-boundary-model in the folder next to theirs.

What the skills need

  • Node 18 or later, for the map scripts.
  • Chrome, Chromium, or Edge, for still images of a map. Without one, visualize-boundaries still draws the map as a page. Set CHROME_PATH if the script cannot find the browser.
  • Access to GitHub, for to-issues to create issues.

With npx skills

It supports Claude Code, Codex, and most other agents.

npx skills add meaningfool/boundary-model --skill '*'
  • -a <agent> picks an agent, such as -a claude-code -a codex.
  • -y skips the confirmation prompts.
  • -g installs for your user instead of the current project.

In a project, the skills go in .agents/skills/, linked into each agent's own folder such as .claude/skills/, and skills-lock.json records the version. To update, run npx skills update. To remove, run npx skills remove --all.

In Claude Code

/plugin marketplace add meaningfool/boundary-model
/plugin install boundary-model@meaningfool

From a shell, run claude plugin marketplace add meaningfool/boundary-model, then claude plugin install boundary-model@meaningfool.

Auto-update is off by default for this marketplace. To update, run claude plugin update boundary-model@meaningfool, or turn on auto-update for meaningfool on the Marketplaces tab of /plugin.

In Codex

codex plugin marketplace add meaningfool/boundary-model
codex plugin add boundary-model@meaningfool

Start a new session to use the skills. To fetch a newer version of the marketplace, run codex plugin marketplace upgrade meaningfool. To remove, run codex plugin remove boundary-model@meaningfool.

Both plugins install the nine skills as one plugin, so each skill's name becomes boundary-model:<skill>, such as boundary-model:extract-boundaries.

By hand

  1. Get the skills 
    git clone https://github.com/meaningfool/boundary-model.git
cd boundary-model/skills
  2. Copy the nine folders into your agent's skills folder 
    mkdir -p ~/.claude/skills
cp -R use-boundary-model extract-boundaries review-boundaries \
  update-boundaries visualize-boundaries shape-boundaries \
  slice refine to-issues ~/.claude/skills/

    These commands install for Claude Code. For another agent, use its skills folder, such as ~/.agents/skills/ for Codex. To share the skills with a team, use the project's skills folder instead.

Keep the folder names, and name each folder as above. Don't copy with a trailing-slash glob such as skills/*/. On macOS, cp -R with a trailing slash copies a folder's contents instead of the folder.

Check it works

Start a new session in a repository and ask: “Map this repository's boundaries.” The agent should load extract-boundaries. Unless you say otherwise, it reads the whole repository except dependencies, generated files and secrets.
